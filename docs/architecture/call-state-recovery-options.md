# Call-State Recovery Options Comparison (Joint-Decision Input)

- **Status:** research comparison; the Redis application-layer necessary-state checkpoint has been explicitly chosen as the direction by the maintainer, but ADR-0023 remains proposed, not accepted and not implemented.
- **Date:** 2026-10-01
- **Scope:** compare the necessary call-state recovery approaches that satisfy REQ-NF-1, under the retained reSIProcate production-stack direction.
- **Online-source access date:** 2026-10-01

This document records the boundaries of the chosen direction and references for future implementation; it does not reopen the storage direction: the current direction is the application-layer necessary-state checkpoint in Redis, not serializing full DUM / `SipStack` objects. PostgreSQL, full native snapshot/replication, and other SIP products are only future-implementation references, not a current proposal on par with Redis, nor a selected solution. ADR-0023 remains proposed; the direction is not yet implemented or formally accepted. The product goal is to recover the state needed for the **explicitly supported recovery point**, and it does not promise that all dialogs or transaction runtime can be recovered today. REQ-NF-1 remains a hard requirement; D10 is still unresolved and blocks M7/M8. See the [requirements](../requirements/prd.md), the [D10 review record](../reviews/d10-state-recovery-gap-review-2026-09-30.md), [ADR-0002](adr/0002-per-usecase-process-state-redis.md), [proposed ADR-0022](adr/0022-resiprocate-b2bua-control.md), and [proposed ADR-0023](adr/0023-redis-call-state-checkpoint.md).

## 1. Standards and Product Boundaries

RFC 3261 defines dialog and transaction as distinct state machines. A dialog identifier consists of Call-ID, local tag, and remote tag; dialog state also includes both sides' sequence numbers, route set, and remote target, among others. A B2BUA's two legs are independent dialogs; a single Call-ID or a business-only mapping cannot substitute for per-leg state. [S1]

The correlation of INVITE/CANCEL/final-response, retransmission, ACK, and transaction timers belongs to transaction behavior. RFC 6026 further requires that INVITE 2xx-related transaction state continue to participate in processing within the specified Accepted state and time limits. RFCs specify online SIP behavior, and **do not specify the persistence format, state-replication algorithm, or high-availability implementation after a process crash**; these are product-design and acceptance options, and must not be mischaracterized as RFCs already requiring Redis or a particular store. [S1][S2]

This project's measured boundary: in reSIProcate 1.14.0, the cross-two-OS-process UAC `makeInviteSession(..., DialogSetId, ...)` path can, after the application restores Call-ID, tags, Contact/remote target, Route, and CSeq, send a same-dialog re-INVITE and receive 200. It does not restore the original `InviteSession` or transaction runtime. Conversely, a real established UAS dialog, after the old process exits, receives a same-dialog BYE from a fresh DUM and actually returns 481; the source path looks up DUM's private map by `DialogSetId` and returns 481 if not found. No UAS rehydrate or SipStack transaction snapshot/restore API was found in the public headers. The two-process two-leg test only passed UAC re-association; it does not cover UAS, pending transactions, or fencing. [S3][D1]

**D10 scope note.** The current D10/REQ-NF-1 [acceptance item](../acceptance/test-plan.md) is strictly limited to recovery of an established dialog after ACK has been exchanged and the INVITE transaction has completed: establish a basic two-leg call, kill and restart the AS, send a same-dialog BYE from the upstream, and verify that the new process restores the UAS/UAC mapping, routes that BYE over the already-established UAC leg to the peer, and that Redis retains the complete dialog record. The new process handles a new BYE transaction; the current acceptance does not require restoring the completed INVITE transaction, nor a transaction that was in flight at crash time. The UAC `DialogSetId` re-INVITE probe is only exploratory evidence, not an acceptance step in the current test plan. This baseline also does not include an in-dialog re-INVITE or BYE initiated by the downstream/UAC after restart. REQ-NF-1 remains a hard requirement. This AS does not carry or anchor RTP (REQ-NF-6/ADR-0004); this acceptance does not test media interruption or recovery. A fresh DUM returning 481 to a same-dialog BYE proves that SIP dialog/control-state recovery has not reached the current baseline; it does not prove RTP interruption. This note introduces no media blocker and adds no media requirement. The "in-flight transaction" column in the matrix compares optional extension capability beyond the current baseline only; any change that brings this behavior into a gate must separately extend/modify the requirement and test plan and obtain explicit maintainer approval.

## 2. Options Matrix

**Decision status:** the Redis checkpoint is the direction explicitly selected this time, not yet accepted by an ADR or implemented. PostgreSQL and full native recovery are unselected future-implementation references; OpenSIPS / Kamailio are external-product references; UAC `DialogSetId` is partial probe evidence; active/standby is an ownership pattern, not another storage choice. The table below compares subsequent implementation details; it does not imply these options are coequal current proposals.

| Mode | Established UAC dialog | Established UAS dialog | In-flight transaction (optional extension beyond current D10 baseline) | Two-leg consistency and durability | Fit and cost for this product |
|---|---|---|---|---|---|
| Application-layer necessary-state checkpoint to Redis | Recoverable via an application snapshot plus a narrow re-association path; currently only UAC probe evidence | Current default DUM path cannot; BYE returns 481; still needs UAS rehydrate extension/mechanism | Not auto-recovered by a dialog checkpoint; pending transactions beyond the current baseline need separate recovery or safe convergence | `MULTI/EXEC` or Lua can compose one atomic Redis execution, but multi-key design, command-error handling, and two-leg versioning and failover semantics still need design; AOF/RDB and async replication bring different loss windows | Continues the ADR-0002 storage direction, but needs write boundaries, recovery adaptation, two-leg atomic checkpoint, and owner fencing; cost medium-high [S4][S5] |
| Application-layer necessary-state checkpoint to a transactional store (e.g. PostgreSQL) | Same as above: a database is not a DUM rebuild API | Same as above: still needs a UAS recovery mechanism | Same as above: the current baseline does not require recovering the pre-crash transaction; if the scope is extended, the database itself also does not recover SipStack transaction state | A single database transaction can commit multi-leg state as one atomically visible unit; synchronous replication can raise the durability of confirmed writes but adds commit-wait/availability constraints | A consistency candidate; in tension with ADR-0002's existing judgment on high-concurrency session storage and latency, needs separate evaluation, cannot rewrite that ADR within this comparison [S6] |

## 3. Evidence and Cost of Future Implementation Options

### 3.1 Redis application-layer necessary-state checkpoint

This is a future implementation constraint of the chosen direction, not current code capability: a subsequent adapter must write the `CallController` necessary business state and each leg's necessary dialog fields into Redis, without saving DUM pointers, `InviteSession` objects, or transaction timers. The checkpoint should update with the defined SIP/session state transitions, and must define the ordering between each external SIP side effect and durable acknowledgement; otherwise the process may crash after a message has been sent but before the state is persisted. The two legs must be committed as one logical snapshot, via a single value or a verified Redis atomic operation, and old owners and half-snapshots must be rejected through generation/owner fencing. [S4]

Redis official docs state that commands inside `MULTI/EXEC` execute in order as one isolated operation, but a runtime error on one command does not roll back the other already-queued successful commands; Lua scripts can compose multi-key operations with atomic execution. So "using Redis" does not automatically equal "all-or-nothing for both legs at the business level": key layout, write validation, and version checking on recovery still need testing. Durability also needs a separate definition: RDB snapshots may lose the most recent few minutes of writes; AOF `appendfsync everysec` is documented with about a one-second write window, `always` is slower; Redis defaults to async replication, and Sentinel failover may lose acknowledged-but-not-replicated writes, and `WAIT` also provides no strong-consistency CP guarantee. [S4][S5]

In the recovery path, it must also be defined: how a write failure prevents the dependent INVITE/CANCEL/final-response, how callbacks stay non-blocking, how the state machine waits for a durable barrier without blocking in the SIP callback, and how an old owner is fenced after Redis failover, and how the active-call TTL avoids expiring before a terminal state. Receiving only an async write-queue acknowledgement cannot be marked as committed. It is consistent with ADR-0002's runtime-store direction, but ADR-0002 does not equal an accepted protocol-recovery semantics, nor does it mean the current StateStore already has these capabilities.

### 3.2 Transactional-store checkpoint

For example, PostgreSQL can write logical call and two-leg records in one SQL transaction, making the commit an atomic unit as seen by other transactions. It still only stores the data the application selects; it does not automatically create a reSIProcate UAS session or SipStack transaction. PostgreSQL streaming replication defaults to async; synchronous commit can wait for standby acknowledgement but adds at least the round-trip-related response latency and is also affected by synchronous-replica availability. [S6]

The main problem for this product is cost and existing architecture: ADR-0002 has already accepted Redis as the runtime-data direction and recorded PostgreSQL's concerns about high-concurrency session read/write and latency. Using PostgreSQL as a recovery-checkpoint candidate is a product choice requiring separate review, not a change to ADR-0002 by this study. It also needs a design for signaling behavior when the database is unavailable, HA failover RPO, connection pooling, and migration/backup.

### 3.3 reSIProcate native recovery and narrow UAC hook

In a pinned reSIProcate 1.14.0 commit, the public `DialogUsageManager` overload `makeInviteSession(..., DialogSetId, ...)` creates a UAC `DialogSet` with the given Call-ID/local tag, not reviving an old `InviteSession`. The same class's `mDialogSetMap` is private; `processRequest()` sends 481 for a non-ACK request with a To-tag but no found dialog set. The `SipStack` public header provides process, transport, send, shutdown, and other interfaces; its transaction controller is an internal member; no snapshot/restore interface was found in the public headers inspected. This source lookup does not prove that a custom extension is absolutely impossible, but it shows the current public-API evidence is insufficient to promise UAS or transaction recovery. [S3]

The existing UAC probe supports one limited option: restore enough fields to construct a new UAC dialog set, then issue a same-dialog re-INVITE to re-associate. It cannot cover UAS BYE, an INVITE/CANCEL awaiting response, 2xx/ACK retransmission handling, the original DUM session handle, or the product CallController's paired mapping. Therefore it can only be a candidate mechanism within a more complete recovery design, not D10 pass evidence. [S3][D1]

### 3.4 SIP server persistence/replication references

OpenSIPS 3.6's `dialog` module supports database mode and synchronizes dialog create/update/delete via clusterer binary replication; at startup it can sync from a seed node. The docs also position the local DB as a dialog restart-persistence fallback when all cluster nodes are down, and state that dialogs not re-confirmed in the cluster sync are discarded. OpenSIPS's `b2b_entities` docs explicitly record the UAS server entity and UAC client entity, can replicate B2B entities via `cluster_id`, and support clusterer sync restart persistence; `b2b_logic` has its own DB mode/logic state. The corresponding cost is clusterer/proto_bin, seed and capability synchronization, DB write-through/write-back strategy, and overall migration verification of SIP behavior. The current official docs' description of TM anycast is to send a response received on a different node back to the owner that created the transaction; this is not a promise to migrate that transaction to a new owner. No complete transaction-recovery proof for this product was found here either. [S7]

Kamailio 6.1's `dialog` module supports DB storage/load, with fields including dialog tags, both sides' CSeq, route set, Contact, and state; `db_mode` has realtime, delayed, shutdown options, and early and deleted states are not written to DB. Its `enable_dmq` option's official description is very specific: DMQ only shares basic dialog info sufficient to sync profiles, and cannot send in-dialog requests on non-original proxy nodes. So this feature can compare DB restoration/cluster ownership, but cannot serve as evidence of complete UAS+UAC two-leg B2BUA or in-flight TM transaction recovery. Kamailio's DMQ replicates, per peer, the data it defines as needing replication; DMQ itself is not an arbitrary SIP transaction snapshot. [S8]

The product docs above are reference patterns and do not change the reSIProcate stack already selected in this repository. Directly choosing OpenSIPS or Kamailio, or adding a SIP server as an external state authority, would each require separate discussion of their fit with the existing Python `CallController`, product requirements, deployment, security, and operations boundaries.

### 3.5 Active/standby state authority

This is an ownership pattern distinct from "all replicas can take over": designate a current SIP-state owner, a backup receives state replication but does not actively perform actions that would affect dialogs; on failure, after an explicit takeover, the new owner takes over. OpenSIPS clusterer sharing tags use `active`/`backup`, and switching active broadcasts and causes the other node to step down to backup; the `dialog` docs list the dialog operations forbidden in backup state. [S7]

This mechanism provides owner semantics worth studying; it does not by itself solve state integrity, in-flight transactions, or old-node isolation, nor does it equal a database lock. To satisfy this project's contract still requires synchronizing both legs' necessary state, verifying takeover atomicity/generation fencing, and making peer routing consistent with the owner. If this pattern is implemented on reSIProcate, the relevant mechanism is not yet designed; referencing OpenSIPS functionality does not mean introducing OpenSIPS.

## 4. Recovery Contract and Open Questions

The current D10 baseline needs to evaluate the following **state categories**, without presupposing a schema: one logical call key; both legs' Call-ID/local tag/remote tag; each leg's remote target and route set; the CSeq needed to construct/process the post-restart new BYE; the `CallController` cross-leg mapping, business state, and configuration context/version; generation/owner fencing when needed; and handling of state termination, expiry, and unrecoverable errors. Exact fields must be derived from the ACK-complete call → restart → upstream BYE trajectory and verified through real SIP replay. Pending INVITE/CANCEL/final-response transaction correlation, next action, and SipStack transaction runtime belong to optional in-flight extensions, not the current D10 acceptance. This list does not imply these fields can be serialized or restored via reSIProcate's public DUM API, nor does it select a storage solution. [S1][S2]

**Current acceptance scope (determined, not an open interpretation):** the D10 baseline for REQ-NF-1/E5 is the ACK-complete established dialog; after restart, the replacement processes the new upstream BYE, routes it over the existing UAC leg to the peer, and verifies the complete dialog record in Redis. The old INVITE transaction has completed after ACK; the current test plan does not require recovering it, nor does it test a transaction that was in flight at crash time.

**Optional future extension (not part of the current gate):** could evaluate an in-dialog re-INVITE/BYE initiated by the downstream/UAC after restart, and recovery or safe convergence of a pending INVITE/CANCEL/final-response/2xx-ACK transaction at crash time. These are not open interpretations of the current test-plan scope; any extension brought into the acceptance gate requires separate or extended REQ/test-plan changes and explicit maintainer approval.

Questions still to be answered before implementation authorization:

- If an in-flight transaction extension is separately approved in the future, for each added recovery point, should it recover the transaction, safely converge per received message, or take some other explicit next step? How to avoid duplicate INVITE/CANCEL/2xx/BYE and erroneous 481?
- What is the durable ordering of the checkpoint write relative to outgoing request/response, the acceptable write latency/backlog, the backpressure on failure, and the Redis/database failure policy?
- For the current established-dialog baseline, how do the two legs commit and take over as one logical unit? How does generation prevent a stale process from continuing to send SIP after the new owner is authorized? How are in-dialog requests routed to the current owner?
- How are the active-call TTL/terminal cleanup defined? When the store is missing, expired, or inconsistent, how to simultaneously avoid silently dropping calls and duplicate/conflicting SIP behavior?
- REQ-NF-1 does not expand RTO/RPO numbers in this design document; the joint decision must define the failure scope, acceptable data loss, and recovery time, and keep them consistent with the original requirement's "ongoing calls must not be dropped."

### 4.1 Per-call state check of the two current apps

Source and corresponding tests show that neither current app's pure decision module writes an app-specific per-call checkpoint:

- [`src/apps/translation/src/as_translation/decision.py`](../../src/apps/translation/src/as_translation/decision.py) only receives request, rules, and translation rules and returns a decision; it has no `StateStore` import/call and no additional business-state payload. Its [unit tests](../../src/apps/translation/tests/test_decision.py) verify pure-function behavior, and the [contract replay](../../src/apps/translation/tests/test_contract_replay.py) only replays decision data. The README describes session state being saved via StateStore in the future, but the current decision source/tests have no corresponding write.
- [`src/apps/anti-fraud/src/as_anti_fraud/decision.py`](../../src/apps/anti-fraud/src/as_anti_fraud/decision.py) receives `Mapping[str, int]` counters, only reads by rate-limit rule ID, does not rewrite counters, does not read the clock or open a socket; [unit tests](../../src/apps/anti-fraud/tests/test_decision.py) explicitly assert that counters are unchanged, and the [contract test](../../src/apps/anti-fraud/tests/test_contract_replay.py) injects counters from case data. `RateLimit` carries `window_seconds`; the decision module separates reading counters from counter/expiry management; the Redis-state direction described in the README does not prove wiring is present, and the current app source/tests have no `StateStore` write.
- Therefore the translation app's extension payload is currently empty; the anti-fraud rate-window counter is a separate aggregate domain state, not a per-dialog field, and should not be copied into a per-call checkpoint. Its counting, TTL, and idempotence semantics should be managed by an independent counter store/use-case adapter; existing code does not prove this wiring is implemented. A future `CallController` that needs AS-specific business recovery data may use the namespaced/versioned extension slot specified by ADR-0023.

## 5. Decision Boundary

The current direction is explicitly the Redis application-layer necessary-state checkpoint, but ADR-0023 remains proposed, and there is no recovery adapter or D10 pass evidence. The PostgreSQL, native recovery, and external SIP products in this matrix are future-implementation references, not coequal direction proposals; any choice replacing Redis must be separately adjudicated. This comparison does not modify ADR-0002, PRD, the reSIProcate stack choice, or the D9/D11 state, nor does it mark D10 as resolved. REQ-NF-1 remains a hard requirement, and D10 continues to block M7/M8.
