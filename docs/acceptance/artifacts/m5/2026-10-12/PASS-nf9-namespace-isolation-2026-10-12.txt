-- 环境与方法 --
同一 kind 集群 kind-as-m5 内两个独立 helm 全栈：
- ns-A：namespace as-m5，release `as`（as-3rdparty-as-*，含 bundled PG/Redis、migrate Job、fleet stub 除外的产品全栈）
- ns-B：namespace as-m5b，release `asb`（asb-3rdparty-as-*，6 个工作负载 + 独立 bundled PG/Redis + migrate Job）
对 ns-B anti-fraud Pod 直连 port-forward 8080，每 1s 探 /health/live 与 /health/ready；中途对 ns-A 执行：pg_ctl fast 停掉 as-3rdparty-as-postgres-0 内 PostgreSQL 进程 + 删除 as-3rdparty-as-translation / as-3rdparty-as-anti-fraud 两个 Deployment。随后恢复 ns-A（等 PG 容器自愈、helm upgrade 重建 Deployment、重启 config-service）。演练前后对比 ns-B 全部 Pod 的 UID/startTime/restartCount。

-- 结论 --
PASS（NF-9）：ns-A 治理库进程被停、两个 AS Deployment 被删并随后恢复的整个窗口内，ns-B 独立全栈 58/58 健康探测为 200，ns-B 7 个 Pod 身份（UID/startTime/restartCount）演练前后逐项不变。namespace + 独立 release + 独立 bundled state store 的隔离在 Pod/进程级故障下成立。ns-A 经 helm upgrade 完整恢复。

-- 观察项（非本批修复，详见 review record） --
- ns-A PostgreSQL 进程恢复后，config-service 的单条共享 psycopg 连接不会自动重连，接口返回 500；重启 config-service Deployment 后恢复（本次实测重启后 rollout 完成秒级）。登记为运维观察项。
- exit code 137 是 pg_ctl fast shutdown 终止客户端会话的表现，PostgreSQL 容器由 kubelet 按 restartPolicy 重新拉起。

- 覆盖 namespace/Deployment/StatefulSet 级故障隔离；两 namespace 共享同一 kind 节点，不覆盖节点宕机。
