防假绿的三处设计（如实说明）
----------------------------
1. **403 必须来自权限检查**：每行 403 都断言响应体 detail 精确等于
   `change submission denied` / `change approval denied` / `change rollback denied` /
   `user management denied`（`_DENIAL_DETAIL`）。CSRF 拒绝（同样是 403，detail 为
   `CSRF validation failed`）、双人原则（detail 为 `creator may not approve this change`）、
   资源不存在（404）都无法满足该行。
2. **双人原则不混进矩阵**：approve 用的变更单由专用 `matrix-submitter`（OPERATOR，
   永不被测角色）创建并提交，故 operator 行的 403 **只能**来自缺 APPROVE_CHANGE，
   不可能来自「提交者不可自审」。双人原则本身另立一条
   `test_creator_may_not_approve_their_own_change` 单独断言（approver 自审 → 403，
   detail == `creator may not approve this change`，且落 DENIED 审计行）。
3. 每条 403 都带 CSRF token 与真实会话，避免用「没登录/没 CSRF」冒充越权被拒。

新增的测试函数与断言
--------------------
1. test_http_boundary_enforces_the_role_permission_matrix（参数化 20 行）
   每个角色登录后发真实 HTTP 请求，断言状态码 == 上表；403 行追加断言 detail == 权限拒绝文案。
2. test_denied_write_at_the_http_boundary_persists_a_denied_audit_row
   viewer 带 CSRF 提交变更单 → **403** 且 detail == `change submission denied`；
   审计表**恰好新增一条**（`_only_new_audit_event` 断言 +1）：
     actor == `matrix-viewer`、outcome == **DENIED**、action == `POST /internal/v1/change-orders`、
     resource == `/internal/v1/change-orders`、before/after 快照均为 None。
   再直连数据库复核同一行，写出所查的表与字段：
     `SELECT actor, action, resource, outcome FROM {pg.audit_store.qualified_table} ORDER BY id`
     —— 表为 `<audit_schema>.<prefix>_audit_events`（`qualified_table` 属性给出带引号全名），
     字段 `actor / action / resource / outcome`；断言四元组
     `("matrix-viewer", "POST /internal/v1/change-orders", "/internal/v1/change-orders", "denied")` 在结果中。
3. test_creator_may_not_approve_their_own_change
   approver 自建自提交后自审 → 403 + 双人原则 detail + 一条 DENIED 审计行
   （action == `POST /internal/v1/change-orders/{change_id}/approve`）。

边界（本证据不算什么）
----------------------
* **本文件不签收 REQ-S-4。** 签收权在维护者；本文件只是层 ②（内部环境真 PG）的补测与取证。
* 本证据**不是**内核层证据（`authorize()` 纯函数矩阵仍由 `services/console/tests/test_access.py`
  覆盖），也不是「所有端点」的证据：每条权限只取了上表**一个代表性端点**。
  挂载同一 `require_*` 调用的其余端点**未逐条枚举**，例如
  `POST|PUT|DELETE /internal/v1/as-instances`（approve，:1043/:1076/:1135）、
  `POST|PUT /internal/v1/managed-rules`（submit，经 :903 的 `create_managed_rule_draft`）、
  `POST /internal/v1/change-orders/{id}/submit`（submit，:1319）、
  `POST .../distribution` 与 `.../reports`、`.../apply`（approve，:1347/:1426/:1586）、
  `POST /internal/v1/change-orders/{id}/reject`（approve，:1777）、
  `POST|PATCH /internal/v1/auth/users`（manage_users，:1924/:1959）。
  它们共用同一个 `require_*_permission`，但「共用实现」不等于「已逐端点验证」。
* 本证据的会话与登录走的是**测试用 `TestClient` + 自签 TLS 基址**（`base_url="https://testserver"`），
  不是真实浏览器 / 真实控制台前端；口令为测试口令，与任何真实账号无关。
* 越权落痕只验证了 **submit × viewer** 一条（外加 approve 的双人原则一条），
  未对矩阵中每一个 403 格都断言审计行。
* 本证据**不覆盖** RBAC 与运营商 PKI / 客户集群的交互（restriction）：环境为
  `dev-win03ib7niepf0` 上的内部 compose PostgreSQL。
