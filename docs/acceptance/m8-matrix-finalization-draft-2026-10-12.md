## §2 Explanation of status terms

`defer` is a status term **newly introduced** by this draft (the matrix's existing status terms are pass / fail / blocked / n-a / open), and **may only be used after maintainer confirmation**. The differences between the three:

| Status term | Meaning | Can it be turned back into pass |
|---|---|---|
| **defer** | The engineering layer has **done its best** in this version; what is missing is one of **an implementation project / an external environment / a maintainer adjudication**; both the rationale and the missing item are registered | **Yes** — once the condition is met (project started / environment in place / adjudication made), it can be turned back into pass |
| **blocked** | A **restriction** — this version **cannot** do it (e.g. from 2026-10-07, no joint debugging with a real operator S-SBC / customer K8s before Close) | Cannot be lifted by engineering effort in this version |
| **n-a** | Never accepted, **never recorded as pass** (e.g. v1.1 scope items, non-goal items, all with rationale) | No — never recorded as pass |

Therefore, among the 10 `defer` rows in this document: F-5 / F-9 / F-11 lack an **implementation project**; NF-13 / NF-14 / NF-15 / D12/O5-HA lack an **external environment or a gate adjudication**; F-8 / F-16 lack **new evidence in this version**; S-1 lacks a **maintainer either/or adjudication**.
