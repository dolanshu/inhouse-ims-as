### M4b-6b durable audit API/store integration (2026-10-02; engineering evidence, not acceptance)
- `PostgresAuditStore` stores actor/action/resource/outcome/time plus canonical before/after snapshots; detail is not persisted. Credential key/value and PEM private-key checks are heuristic; a producer allow-list/redaction is still required. The snapshot cap is 64 KiB, and safe metadata has length/character boundaries. The dedicated non-public schema is established through explicit migration/owner setup; catalog/object, column/default/constraints/triggers, and ascending bigint sequence are checked; partition/publication are not supported, and a history guard is retained to prevent sequence regression. Owner triggers block mutation/truncate. The runtime role is NOLOGIN, has no CREATEROLE/membership, and has only schema USAGE, table SELECT + INSERT excluding `id`, and sequence USAGE/SELECT; no schema CREATE / table mutation. The role is validated at startup, and a separate login role must `SET ROLE`.
- The default `create_app` requires a durable audit store; only the explicit `allow_unaudited_callback_mode=True` permits the legacy/test callback mode, and that is incompatible with session auth. Request-level serialization with an exactly shared PG connection; audited writes are staged with `commit=False` and then committed in the same transaction as the audit append; on business failure the mutation is rolled back and DENIED/null snapshots are written; when audit is unavailable a generic 500 fail-closed is returned. All requests audit allowed/denied; the internal API catchall covers unmatched GET/HEAD and POST/PUT/PATCH/DELETE/OPTIONS/TRACE/CONNECT while preserving identity/permission/CSRF checks. The session path uses a template plus a full HMAC-SHA256 digest over sorted parameter names and does not store the raw path/query; a stable 32-byte key is configured externally, and rotation breaks cross-period correlation.
