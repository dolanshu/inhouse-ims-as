## 2. Review Q&A (2026-10-07)

### How REQ-S-2 / REQ-S-3 count as passing

The text in §3 of [`test-plan.md`](../acceptance/test-plan.md) is: the SIP between the AS and the S-SBC goes over TLS, cleartext 5060 is rejected, and the certificate chain is issued by the **operator PKI** (S-2); calls in progress during the rotation window are unaffected, new connections use the new certificate, the old certificate is rejected after expiry, and the process is not restarted (S-3).

The M7.1 test CA proves the transport and the rotation mechanism. Signing pass against that text requires an issuing chain from the operator PKI. No operator PKI is used before Close, so these two cannot be signed pass before Close. To sign them pass before Close, the maintainer must rewrite the "operator PKI" sentence in test-plan so that equivalent behaviour on the test CA is accepted. M7.1 does not change this framing.

### How CPS / SLA can be published

What is published externally is the O1 target written by the maintainer, not the count from some demo run. The path is §5.1 O1 and the M6 row of §4 of [`plan.md`](../plan.md): the dev-host measurement report already exists, and the **target adjudication is still open**. Only after the adjudication is written into CPS, concurrent sessions and call setup latency does it enter the external framing and the HPA thresholds. What AGENT.md §2 forbids is treating the measured value as a commitment before that point. The M7.1 result page may show the number of calls sent and the latency of that one run, labelled as not a capacity commitment.

### Where the deliverable of ADR-0014 lives

ADR-0014 does not have a product feature list. It specifies the three testbed layers: `contracts/`, `simulators/` and `load/`, and states that the testbed is not delivered with the product. Whether the customer uses the testbed for acceptance is **D6** in §5.2 of [`plan.md`](../plan.md), still pending. This document does not call it v1 or v1.1: §0 of `plan.md` already records that the repository has no definitions of those two versions.

The product itself is in M2–M5 of plan §4 (kernel, translation and anti-fraud, console, Helm). The testbed is in the repository structure in plan §2.1. `load/` was done by M6. The S-SBC simulation in `simulators/` is written in both ADR-0003 and ADR-0014, while the `as_simulators` package is still empty. That is a missing layer in the test assets, not a scope omission in the product. What M7.1 fills is that layer, and it is still not an artifact handed to the customer together with the product.

### When REQ-S-4 is accepted

REQ-S-4 accepts the authorization and audit of the **product console** (test-plan §3: every write operation checks authorization, RBAC, and audit is tamper-proof). plan §5.4 puts formal all-green at **M8, or a separate maintainer sign-off**. The 2026-10-04 signature of M4b-6a / 6b is an engineering slice, not the acceptance of this REQ. REQ-S-4 is still open in the matrix.

This review: the test tool UI does not need login; the product console must have user management. Here user management means login and basic accounts on the product console (the ADR-0024 engineering slice is already in place). The full UM in plan §5.3 (SSO, MFA, the full account lifecycle) is still an un-requirements'd gap, marked n-a in the matrix, and the product scope is not expanded here.

The simulation platform page lives in `ims-sim`; it does not attach the product console's Ingress and does not reuse the product login session, so that a demo run is not recorded as REQ-S-4 having been signed off.

The M8 next-step plan remains on hold.

## 3. Proposed topology (for review)

Two namespaces:

| namespace | What is inside |
|---|---|
| `as-sut` | the AS under test (translation / anti-fraud) deployed by the existing Helm chart, its Redis and its configuration plane. It reuses the existing chart; simulation switches are not written into the production values |
| `ims-sim` | simulated S-CSCF, simulated S-SBC, peer UAS, call load generator, test UI |

The network is cut according to the transparent bridge of ADR-0003:

```text
UI / call load  →  仿真 S-CSCF  →  仿真 S-SBC  →  被测 AS  →  仿真 S-SBC  →  对端 UAS
                   （ims-sim）      （ims-sim）    （as-sut）
```

The load generator sends the INVITE only to the simulated S-CSCF. A NetworkPolicy guarantees it cannot reach the AS's SIP port directly; the AS only accepts SIP from the simulated S-SBC. That way the peer in the demo is a "simulated IMS" rather than yet another loopback socket.

To the upstream, the simulated S-SBC presents "the AS is inside the network"; to the AS it presents "I am the S-CSCF", and messages are forwarded as a transparent bridge. This is behaviour the POC `src/s_sbc_mock` has already demonstrated; the implementation uses this repository's reSIProcate path, not sippy.

The TLS material exists only in the test CA of `ims-sim`. The UI states in fixed text "not the operator PKI".

## 4. Call types and load

POC reference (`3rdparty_AS_POC/docs/phase3-plan.md` D7, `tools/call_load_generator.py`):

| POC type | Behaviour | Recommendation for the first version of this milestone |
|---|---|---|
| T1 +86 E.164 → 0-prefix forwarding | translation connects | **included in the first version**, aligned with callee + prefix |
| T2 0-prefix keep forwarding | translation connects | may be included in the first version, still a prefix rule |
| T3 00 → + forwarding | translation connects | may be included in the first version |
| T4 short number, no match → 404 | 404 | **included in the first version** (corresponds to S2) |
| T5 reachable next hop → 200 | basic connection | **included in the first version** (corresponds to S1) |
| T6 unreachable next hop timeout | failure | second phase. The current `as_load` does not do UDP retransmission timing |
| F1 allowlist calling forwarding | anti-fraud passes | included in the first version, if the anti-fraud application can already run in the namespace under test |
| F2 blocklist → 608 | anti-fraud rejects | included in the first version. If the product path is still 603, the UI shows the actual response code and does not rewrite it as 608 |
| F3 high-frequency calling → 608 | anti-fraud rejects | second phase. The current product has no such rule axis |
| F4 missing PAI, fail-open | anti-fraud passes | second phase. First confirm whether the product has this policy |

The POC's hold-time model (hold 2 s / 8–15 s / 20–30 s after about 1 s of connection, plus a small number that do not connect) is worth borrowing for a **configurable hold time**. The current `as_load` smoke test uses hold=0, and its concurrency equals the cumulative number of setups, so it cannot serve as a multi-call demo.

First-version load knobs:

- transport: UDP / TCP / TLS
- the enabled call types (the subset marked "included in the first version" in the table above)
- target CPS
- duration
- hold time (or target concurrency). At least one of the two is not 0

The analysis page gives at least: the number sent, the final response code distribution, the number connected, the number failed, setup latency, and buckets by call type. The SIP ladder is deferred to the second phase.

## 7. Review conclusions (2026-10-07)

1. **The simulated S-SBC is one process inside this platform**, running in `ims-sim`. It performs the transparent bridge per ADR-0003: the SIP arriving from the simulated S-CSCF is forwarded unchanged to the AS under test, and the AS's responses are returned unchanged. It is not an operator's device, and it is not the UDP socket in today's tests that sends the INVITE straight to the AS. The load generator connects only to the simulated S-CSCF; the NetworkPolicy denies the load generator direct access to the AS's SIP port.
2. **Kamailio is not in the first version.** Confirmed. The first implementation is exactly the transparent bridge above.
3. **The simulation platform chart is separate from the production chart.** Confirmed. Simulation workloads do not enter the default values of `deploy/helm`.
4. **The environment starts with kind.** Getting kind working is this milestone's environment.
5. **Call load does not do UDP retransmission, and does not do forking.** UDP retransmission is instead covered by unit tests. There are currently no retransmission cases in the `platform/` tests; M7.1 adds them. If retransmission happens inside reSIProcate, the test belongs in the unit or contract layer where the resent messages are visible, not in the load generator.
6. **Do not commit pcaps, private keys, or the test CA's long-term keys.** The test CA is generated at startup, or only already-gitignored local material is used.
7. **Rewiring the demo stories to this platform** happens after M7.1 is complete; it is the same follow-up as the demo re-evaluation at the top of this document, and is not part of starting this milestone. Confirmed.
8. **The test tool UI has no login. The product console must have user management** (login and basic accounts). The scope of the full UM is in §2 REQ-S-4.
